## 0. 結論の要約(10 行)

1. **保護はハードに置く。** SVMax・I0Set・Trip・RUp/RDWn・HVMax(トリマ)はクレート側の値が「本物」。ソフトはそれを**表示し、超える要求を拒否する**だけで、**クランプして通さない**。
2. **ソフトは状態を持たない。** 画面に出るのは毎周期のリードバックだけ。「要求した値」は別の列に、別の色で、送信時刻つきで出す。
3. **書き手は常に複数**(GECO、フロントパネル、自分、将来の別スクリプト)。だから「書く → 読み返す → 一致を確認 → 一致しなければ赤で出して止まる」を全書き込みの不変条件にする。
4. **ランプはハードに任せる。** V0Set を 1 回書けば A1833 が RUp で勝手に上げる。ソフトで刻む「ソフトランプ」はネットワーク断で中途半端に止まるので作らない(MHV-4 も SRA で同じ)。
5. **トリップはソフトで自動復帰しない**(初版)。トリップは物理情報。人が理由を書いてから復帰する。
6. **初版の書き込みは V0Set と Pw(ON/OFF)だけ**、対象は SY5527 の 24 ch だけ。保護パラメータの変更と MHV-4 は初版の範囲外。
7. **監査ログは append-only + Grafana に注記**。誰が・いつ・どの ch を・いくつからいくつへ・結果(rc)・読み返し結果。外部(GECO 等)による変化も「外部変更」として同じログに残す。
8. **確認 → 差分プレビュー → 実行** の 3 段。1 回の変化量に上限(例 50 V)。全 OFF だけは 1 動作。
9. **DAQ とは別プロセス・別 UI**。Operator は Start 時に HV の読み値をラン記録に写す(取れなければ「取れなかった」と記録)。Start を止めるかどうかはユーザー判断。
10. **公開 repo なので本物の機器の挙動を模したシミュレータは入れない。** テストは「実機で録った応答の再生」+「書き込み層の許可リスト検査」+「dry-run」+「段階的コミッショニング」で賄う。

## 2. 安全モデル — どの制限をどの層に置くか

### 2.1 層の考え方(内側ほど信用できる)

| 層 | 何が守るか | 誰が変えるか | ソフトの役割 |
|---|---|---|---|
| L0 物理 | A1833 の **HVMax トリマ**(ボード全 ch 共通、ソフトから読める)【資料: A1732/A1832 manual Rev.5 §2.1, §2.4.4】、HV EN 入力(GND に落とさないと全 ch 無効)【同 §2.1, §4.2】、クレートのインターロック | 人が現場で | **読んで表示する**だけ |
| L1 クレート内の保護パラメータ | **SVMax**(ch ごと、1 V 分解能、これを超える値は設定できない)【同 §2.1】、**I0Set + Trip**(過電流を何秒許すか。1000 = 定電流動作、<1000 = 時間後に OFF)【同 §2.1; Hall A wiki】、**RUp / RDWn**(1〜500 V/s)【同 Table 2.1】、**Pw の PDwn(Kill/Ramp)**、**POn**(電源投入時に前回の Pw を復元するか)【資料: Hall A wiki】 | GECO / 専門家 | 初版は**読んで表示 + 要求の事前検査に使う**。書かない |
| L2 アプリ内の運用制限 | 1 回の変化量上限、ch ごとの運用上限(SVMax より低く)、全 ch 同時変更の禁止/許可、書き込みレート | 設定ファイル(repo 管理) | 要求を**拒否**する。クランプしない |
| L3 人 | 確認ダイアログ、差分プレビュー、コメント必須 | 操作者 | 迷ったら止まれる UI |

**なぜ L1 をソフトで書かないのか【判断】**: 保護パラメータは「普段触らない・触ると壊れ方が変わる」ものなので、普段使いの Web UI から変えられると、SVMax を上げてから V0Set を上げる、という「安全装置を外してから踏む」操作が 2 クリックでできてしまう。保護は GECO(別のツール・別の心構え)に残し、Web アプリは「保護の内側で動く」ものに留めるのが筋。将来必要なら **別ロール・別画面** で足す。

### 2.2 ソフトが「できてはいけない」こと(初版の不変条件)

- SVMax / HVMax / I0Set / Trip / RUp / RDWn / PDwn / POn / SetChName / SetSysProp を**呼ばない**(許可リスト。モニタと同じく、ソースに `CAENHV_Set*` が V0Set と Pw 以外に現れないことをテストで固定)。
- 要求値が SVMax(読み値)以上なら**拒否**。`hv_control.py` のように SVMax に丸めて書くのは、操作者が「1900 V を頼んだのに 1800 V で通った」ことに気づかない経路を作る(警告ログは出るが UI には出ない)。
- SVMax が**読めなかった ch には書かない**(`hv_control.py` はここは正しく拒否している)。
- **読み値が古い状態で書かない**: 直近 N 秒以内のリードバックがない ch への書き込みは拒否(接続断の直後に古い画面で操作する事故を防ぐ)。
- ソフトランプ(ループで少しずつ V0Set を上げる)を**実装しない**(§4.4)。
- 複数 ch への一括書き込みは、ch ごとに個別の読み返し結果を出す。1 つでも失敗したら「部分成功」を赤で出す(全部成功したふりをしない)。

### 2.3 ハード側で事前に決めておくべき値(ユーザー作業、GECO で)

- 各 ch の **SVMax** を「運用値 + 余裕(例 100〜200 V)」に下げる。今は何 V か未確認(モニタは SVMax を読んでいない)。これが一番効く安全装置で、ソフトに何かあっても超えられない。
- **Trip** を有限にしておく(1000 = 定電流 だと過電流が無期限に続く)【資料: A1732/A1832 §2.1】。PMT の場合の妥当な Trip 時間はユーザー判断。
- **RUp / RDWn** を PMT に合った値に(ソフトはこれを変えない前提なので、ここが唯一のランプ速度)。
- **POn**: 停電復帰時に自動で ON に戻るのが望ましいか(ビーム中の停電なら戻ってほしい、作業中なら困る)。ユーザー判断。
- **PDwn**(Kill か Ramp か): OFF 命令で即落とすか RDWn で落とすか。PMT なら Ramp で十分だが、緊急用の `Kill` コマンドは別にある(§4.6)。

## 3. 書き手は複数いる — 状態を持たず、常に読み返す

### 3.1 「シングルライター」は成立しない

GECO、クレート前面パネル、HiVoCS(Web)、クレート内蔵の EPICS サービス、将来のスクリプト、全部が同じ設定値を書ける。ロックする仕組みはクレートにない(SY1527 系に Guest/User/Administrator の 3 段階はある【資料: A1732/A1832 manual p.4】が、排他ではない)。だから設計は「**他人が黙って変える前提**」で組む。

### 3.2 不変条件: 書く前に読む、書いた後に読む

1. **書く前**: 対象 ch の V0Set / Pw / Status / SVMax / VMon / IMon を**今**読む。画面の値ではなく今の値。
2. **前提条件つきの書き込み(compare-and-set)**: 操作者が画面で見た値(例 V0Set = 1450)を要求に添え、送信直前の読み値と違っていたら「誰かが変えた(1450 → 1500)。もう一度確認して」と**止める**。これが GECO との競合を検出する唯一の方法【判断】。
3. **書いた後**: 同じパラメータを読み返す。V0Set は即座に一致するはず。一致しなければ rc が 0 でも**失敗扱い**。
4. **ランプの監視**: VMon が V0Set に収束するまで(Status の RampUp/RampDown ビットが落ちるまで)を「進行中」として表示し、タイムアウトしたら警告。`hv_control.py::wait_ramp` は VMon と VSet の差だけ見て Status を見ていないので、トリップして 0 V に落ちても「タイムアウト」としか分からない。**Status ビット**(bit0 ON, bit1 RUp, bit2 RDn, bit3 OVC, bit4 OVV, bit5 UNV, bit6 ExtTrip, bit7 MaxV, bit8 ExtDisable, bit9 IntTrip, bit10 CalibErr, bit11 Unplugged, bit13 OVP, bit14 PowerFail, bit15 TempErr)【資料: CAEN HV Wrapper Rev.16 p.10】を一次情報にする。

### 3.3 「ソフトは状態を覚えない」を具体化する

- 画面の全ての値はリードバックの**タイムスタンプ付き**。古くなったら(例 10 s)値をグレーにし「最終更新 xx:xx:xx」を出す。
- 「要求値(requested)」は別列。要求してから一致するまでは「要求 1500 / 実際 1450→…」と両方出し、一致したら要求列を消す。要求列はセッションが落ちたら消えてよい(再接続後は読み値だけが真実)。
- ON/OFF は **Pw の読み値**と **Status bit0** の両方を見る(Pw=1 でも ExtDisable や Trip で出ていないことがある)。表示は「Pw: ON / 出力: あり(VMon 1498 V)」のように分ける。
- **外部変更の検出**: 自分が書いていないのに V0Set / Pw / SVMax / I0Set / RUp / RDWn / Trip が前回読みと違えば「外部変更」イベントとして監査ログと Grafana 注記に残す。これで「GECO で誰かが触った」が後から追える。前回読みを使うのは変化検出のためだけで、真値としては使わない。
- SysProp `Sessions`(接続中ユーザー一覧)【資料: Wrapper Rev.16 p.13–14】が SY5527 で読めれば「今 GECO も繋がっている」と画面に出せる(要実機確認)。

### 3.4 なぜ重要か — 実例

JLab の SY4527 + A1535 試験では、クレート内蔵 EPICS サーバの PV と GECO2020 の表示が食い違い、VSet 1500 V → 1 V、RDwn 25 → 1 V/s のような「勝手に変わった」値が観測され、再設定・ON/OFF し直し・EPICS サーバのリセットで回復した【資料: JLab DSG Note 2019-30, Table II】。つまり**同じクレートを 2 経路で見ると違う値が見えることがある**。自分の経路(CAENHVWrapper)で書いて自分の経路で読み返す、を徹底し、ときどき GECO の表示と突き合わせる運用が要る。

## 4. コマンドの意味論

### 4.1 確認 → 差分 → 実行

- 操作は「編集モードで値を溜める → 差分一覧(ch 名・現在値・要求値・Δ・SVMax・判定)を出す → コメントを書いて実行」。GECO 風の「セルを書き換えたら即送信」はしない【判断】。
- 差分一覧の段階で L2 の検査(Δ 上限、SVMax、古い読み値、他人の変更)を全部済ませ、**1 つでも NG があれば全体を送らない**(部分実行は混乱のもと)。
- 全 OFF(§4.6)だけは例外で、確認 1 回で即実行。

### 4.2 1 回の変化量の上限(step limit)

- PMT なら例 50 V/回(`hv_calibration` の既定と同じ)。目的はタイプミス(1500 → 15000、1500 → 150)を止めること。大きく変えたいときは複数回に分ける。
- **上限は Δ だけでなく絶対値にも**: ch ごとの運用上限を設定ファイルに持ち、SVMax より低く置く(SVMax は「壊れない」線、運用上限は「普通はここまで」の線)。
- Δ は**今の読み値**に対して計算する(画面の古い値や、自分が前に送った値に対してではない)。

### 4.3 冪等性と再送

- 要求は常に**絶対値**(V0Set=1500)で表す。「+50 V」のような相対要求を API に持たせない(再送で 2 回足される)。
- 各要求に ID を付け、同じ ID の再送は no-op。ブラウザの「送信ボタン二度押し」「再読み込みで再 POST」をここで吸収する。
- 前提条件(§3.2 の 2)があるので、再送しても前提が変わっていれば自然に拒否される。

### 4.4 ランプはハードに任せる — ネットワーク断の扱い

- A1833 は V0Set を書いた瞬間から RUp/RDWn で自走する。ソフトとの通信が切れても**ランプは完走する**。これは安全側(途中で止まらない)。だからソフトは「書く → 見守る」だけで、刻んで書かない。
- 通信断の間に起きたこと(トリップ、外部変更)は、再接続後の**全 ch 全パラメータ再読み**で拾う。再接続時に「切れる前に送ろうとしていた要求」を**自動で再送しない**(状況が変わっているかもしれない)。
- CAENHVWrapper の注意: SYx527 は **30 秒の通信タイムアウト**があり、何も送らないと切られる。15 秒ごとに `GetSysProp("SwRelease")` のような keep-alive を推奨。切れたら **DeinitSystem してから** InitSystem し直す必要がある【資料: Wrapper Rev.16 p.5】。ポーリングしている限り自然に満たすが、書き込み専用の接続を別に持つ設計なら注意。
- `hv_calibration` のゲインマッチングのような「測って → 書いて → 待つ」ループは、ループを回すのがソフトなので、ループ自体がネットワーク断に弱い。やるなら「1 反復 = 1 つの確認済みコマンド集合」に分解し、各反復の前に全読みする(初版の範囲外)。

### 4.5 トリップ

- **初版では自動復帰しない【判断】。** トリップは「電流が I0Set を Trip 秒以上超えた」=放電・光漏れ・ケーブル・検出器の異常の兆候。自動で ON し直すと、原因を温存したまま同じことを繰り返し、PMT を傷める。ATLAS NSW の DCS は "Reset Trip" を自動化の一つに挙げている【資料: ICALEPCS2021 MOPV009 §Requirements】が、それは専門家が条件(回数上限・待ち時間・ビーム状態)を組んだ上での話で、初版の小さなシステムで真似る理由はない。
- 復帰手順(人): トリップ ch を表示 → 操作者がコメント(推定原因)を書く → `Pw=ON`(クレートはこれで Tripped をクリアし、RUp で再び上げる【資料: Hall A wiki "Tripped… until Clear Alarm"; "turn On again"】)。`ExecComm("ClearAlarm")` はクレート全体のアラームをクリアするコマンドなので、ch 単位の復帰には Pw を使う方が狙いが明確【判断】。
- 表示: Trip 中は VMon が 0 で Pw が 0 になっている(RDWn で落ちた後)。「OFF」と「Tripped」を見分けるには Status の bit9(IntTrip)/bit6(ExtTrip)が要る。モニタの `status` フィールドはこれを既に Influx に書いているので、Grafana のアラート(TODO 74 P6)の最初の題材にもなる。
- 後から足すなら: ch ごとに「自動復帰を許可(回数 N、間隔 T)」を**専門家ロールで**設定、復帰のたびに監査ログ。

### 4.6 緊急 "全 OFF"

- 2 通りある: (a) 全 ch `Pw=0` → RDWn で降りる(PMT に優しい)。(b) `ExecComm("Kill")` = **クレート内の全 ch を即座に落とす**【資料: Wrapper Rev.16 p.12】。Kill はクレート内の他ボード(今はない)も巻き込む。
- 初版は (a) を「ALL OFF」ボタンにし、(b) は「KILL(緊急)」として別の、わざと押しにくい場所に置く【判断】。どちらも**送った後に全 ch を読み返して結果を一覧で出す**(1 ch でも落ちていなければ赤)。
- 全 OFF は確認ダイアログ 1 回だけ。多段確認にすると緊急時に遅い。

### 4.7 失敗を黙らせない(このプロジェクトの文化)

- rc ≠ 0、読み返し不一致、タイムアウト、SVMax 超え、前提条件不一致、部分成功 — すべて UI の目立つ場所と監査ログの両方に出す。ログだけ・UI だけ、にしない。
- 負の rc は電源側からのエラー(例 −5 = Parameter not present、TODO 76 で `VSet` 事件)【資料: Wrapper Rev.16 p.20 注記】。rc を**数値のまま**残す(文字列に丸めると後で調べられない)。
- `hv_control.py` の `_get_float_param_fallback` が失敗時に `0.0` を返すのは、この文化に反する典型(読めなかったのか 0 V なのか区別がつかない)。制御アプリでは「読めなかった」は値ではなく状態として扱う。

## 5. アクセス制御と説明責任

### 5.1 誰が書けるか【判断、ユーザー判断事項】

小さなラボで現実的なのは次の段階。初版は (2) を推奨。

1. ネットワークだけで絞る(pf-qaq のローカル + ユーザールームの LAN + ssh トンネル)。Grafana と同じ露出。誰が押したか分からない。
2. (1) + **書き込みには操作者名(必須、自由記述)+ 書き込み用の合言葉**。閲覧は匿名可。合言葉は repo に入れない(docker/.env と同じ扱い)。説明責任は「名前を書く文化」に依存するが、監査ログに名前が残る。
3. アカウント管理(ログイン、ロール: viewer / operator / expert)。保護パラメータの変更や自動トリップ復帰の設定を expert だけに許すなら必要になる。初版には重い。

付随して: アプリがクレートに繋ぐアカウントは admin ではなく**専用ユーザー**(SY1527 系の User レベル)を作っておくと、`Sessions` で「アプリの接続」と「人の GECO」が区別でき、admin のパスワード変更に巻き込まれない【判断。SY5527 のユーザーレベルの詳細は未確認、HiVoCS の管理画面で設定】。

### 5.2 書き込み可能状態を「武装」する【判断】

閲覧モードが既定で、書き込みは「編集開始」ボタンで明示的に入り、一定時間(例 10 分)無操作で自動的に閲覧モードへ戻る。ssh トンネルで開きっぱなしのタブからの誤操作を減らす。

### 5.3 監査ログ

- **append-only**(JSON Lines 1 行 1 イベント)。少なくとも: 時刻、操作者名、接続元、要求 ID、ch(slot/ch/名前)、パラメータ、**書く前の読み値**、要求値、rc、**書いた後の読み値**、ランプの結果(収束/タイムアウト/トリップ)、コメント。
- 同じ内容を **InfluxDB に注記**として書き、Grafana の VMon/IMon グラフに縦線で出す(ランの注記と同じ仕組み、TODO 74 P5)。「あの時間にゲインが変わったのは誰が何をしたからか」がグラフ上で読める。
- **外部変更**(§3.3)も同じログに入れる。これが LabVIEW 時代の「表示と実機が食い違う」問題への直接の答え: 食い違いを隠すのではなく、食い違った瞬間を記録する。
- ログファイルは `/data` か `/archive` に置き、DAQ のログと同じ保全ポリシーに乗せる。

### 5.4 ラン記録との関係

- **各ランの開始時に HV の読み値(24 ch の V0Set/VMon/IMon/Pw/Status + SVMax)をラン記録に写す**ことを推奨。理由: Grafana の履歴は残るが、「run 123 の HV はこれ」と**一次記録に書いてある**ことが解析時の価値。MongoDB の `config_snapshot` に相当する場所が既にある。
- ただし Operator が HV アプリに依存して Start できなくなるのは本末転倒。**短いタイムアウトで取り、取れなければ「取れなかった」と記録して進む**(初版)。Start を止めるかどうかは §7。
- 読み元は HV アプリの読み取り専用エンドポイントでも InfluxDB の直近値でもよいが、「Start の瞬間の値」を名乗るなら前者【判断】。

## 6. 危険な操作の UI/UX

- **要求と実際を同じセルに出さない。** 列を分けるか、編集中の値は枠線色を変える。送信後は実際値だけが残る。
- **ch を間違えない工夫**: ch 名(NWA01…)を主キーに表示、slot/ch 番号は補助。行の選択→編集→差分一覧で「どの行を変えるか」を 2 回見せる。
- **グループ/プリセット**: 「全 ch を標準運用値にする」「A ボードだけ」のようなプリセットはファイルで持ち(repo 管理、変更履歴が git に残る)、**適用は差分一覧を経由**。プリセットの値を「正解」として表示に使わない(状態を持たないルール)。
- **危険ボタンの配置**: ALL OFF は赤・大きく・独立。KILL は別のカードで、クリック後にテキスト入力(例 "KILL")を要求するくらい重くてよい(§4.6 と矛盾しない: ALL OFF が速い方の手段)。
- **モバイル/狭い画面での誤タップ**: 書き込み系の操作はダブルタップ不可・スワイプで変わるコントロール(スライダー)を使わない。
- **接続状態を常時表示**: クレート接続(最終成功時刻)、`Sessions`、自分が編集モードかどうか。
- **色の意味を固定**: ON=緑、ランプ中=黄、OFF=灰、Trip/Error=赤、読み値が古い=グレー斜線。ATLAS の FSM 状態(OFF / RAMP_UP / RAMP_DOWN / ON / TRIPPED / UNKNOWN / UNPLUGGED)【資料: MOPV009 Fig.6】は、ch 1 本の状態語彙としてそのまま借りられる。UNKNOWN(読めない)を**状態として持つ**のが要点。

## 7. DAQ との関係

- 別プロセス・別ポート・別 UI。Operator は HV アプリの死活に依存しない。
- Operator 側に欲しいのは 2 つだけ【判断】: (a) Start 時の HV スナップショット(§5.4)、(b) Operator UI に「HV: 24/24 ON、Trip 0」程度の**表示**(HV アプリかInfluxDB から読む、数秒のタイムアウト、取れなければ「不明」)。
- **Start を止めるか**: 初版は「警告のみ、止めない」を推奨。HV 未達でも較正ランやノイズランは撮る。止める(インターロック)にするなら、ユーザーが「HV 条件を満たさないと Start できない」ルールを明文化してから。
- 逆方向(DAQ の状態を見て HV を変える、例: Stop したら下げる)は**作らない**。自動化が検出器を触る経路を増やさない。
- HV アプリの書き込みは Operator から**呼べない**ようにする(Operator に HV 書き込み用の HTTP クライアントを置かない)。「DAQ に組み込むのは危険」という決定をコードの構造で守る。

## 8. 機器別の注意

### 8.1 SY5527 + A1833(PMT 24 ch)

- 確認済みのパラメータ: V0Set(VSet は存在しない)、VMon、IMon(µA)、Status、Pw【実測】。A1832 系の一覧は V0Set/I0Set/V1Set/I1Set/Rup/RDWn/Trip/SVMax/Vmon/Imon/Status/Pw/Pon/PDwn/TripInt/TripExt【資料: Wrapper Rev.16 p.9, p.15】。**A1833 で同じかは `GetChParamInfo` で実機から取って固定する**(A1833 マニュアル未取得)。
- `GetChParamProp` で Minval/Maxval/Unit/Exp/Decimal/Mode(RDONLY/WRONLY/RDWR)が取れる【資料: 同 p.7, p.10】。アプリの入力検査はこれ(機器が言う範囲)と SVMax(機器が言う上限)と L2(自分の運用上限)の 3 つを AND で使う。
- Status の OVV/UNV は「出力が設定値から FS の 3% 以上ずれている」【資料: A1732/A1832 §2.1】。ランプ中は UNV が立つのが正常なので、UNV 単独でアラームにしない(RUp ビットと組み合わせる)。
- Pw=ON はインターロック非アクティブ・CH OUT ENABLE 有効のときだけ実際に上がる【資料: Hall A wiki】。Pw を 1 にして rc=0 でも出力がないことがあるので、ON の確認は Status bit0 + VMon で。
- イベントモード(Subscribe)はクレート→PC への**着信 TCP** が必要でファイアウォール設定が絡む【資料: Wrapper Rev.16 p.21】。24 ch なら 1〜2 s ポーリングで十分。初版はポーリング【判断】。
- モニタ(読み出し専用プロセス)と制御アプリを同時に繋いでよいか: 読み出し確認時に GECO と共存できていたので複数セッションは可【実測】。初版は**モニタはそのまま、制御アプリは別接続**でよい(制御アプリの読み返しは自分の接続で行う。Influx 経由の値は検証に使わない)。将来 1 本化してもよいが、今動いているものを壊さない。
- クレート内蔵 EPICS(HiVoCS ≥1.30)【資料: caen.it EPICS IOC ページ】という選択肢もあるが、EPICS のスタックを持ち込む上、JLab の報告【資料: DSG 2019-30】で PV と GECO の不一致が出ている。この規模では CAENHVWrapper 直結が単純【判断】。

### 8.2 MHV-4(Si 4 ch)— 初版の範囲に入れないことを推奨【判断】

理由:
1. **ON/OFF も設定値も読めない**(V4.2 で `RUP` が ERROR、状態読みのコマンドなし)【実測】。「書く → 読み返す」の不変条件(§3.2)が成立しない。書いた `SU` が効いたかは、ランプが終わって `RU` が動いて初めて分かる。
2. **Si は壊れやすい**。MHV-4 は電流上限超過で自動シャットダウン(既定で有効、`AS` で変更可)し、LED 点滅で「再度 ON するまで OFF」になる【資料: MHV-4 V4.0_02 p.3】が、その状態もリモートから読めない。
3. 4 ch だけ、装置は DAQ PC のすぐ横、運用はフロントパネルで足りる(ユーザー決定済)。
4. シリアルポートは 1 プロセスしか開けない。制御を足すなら今の読み出しモニタと**同じプロセス**に統合する必要があり、「書けないことがテストで保証されたモニタ」という今の美点を失う。

それでもやるなら(後日):
- 書くのは `SU`(電圧)だけ。`SP`(極性: HV が出ていれば自動で切って 0 V にする)、`SRA`(ランプ速度)、`SIL`(電流上限)、`AS`(自動シャットダウン)、`SUL`(電圧上限)は**絶対に Web から送らない**。これらは Si の保護そのもの。
- ランプは SRA の設定(5/25/100/500 V/s)でハードが行う【資料: 同 p.6, p.9】。Si 用なら 5 V/s のまま。ソフトで刻まない。
- 1 回の Δ を小さく(例 10 V)、書いた後は `RI` を見続け、電流が上限に近づいたら**それ以上の要求を拒否**(自動で下げるのではなく、人に知らせる)。
- 「設定値が読めない」を UI に正直に書く: 「設定値: 不明(V4.2 は読めない)/ 測定値: 132.5 V」。
- RC バス経由の制御(MRC-1)にはミラーページ(書いてから `CP` で一括反映)と読み出し専用アドレス(ハードの実状態)がある【資料: 同 p.7–8】。USB にはないが、「書き込み領域と読み出し領域は違う値を返しうる」という機器側の思想は、ソフト側の「要求 vs 実際」分離と同じ。

## 9. 検出器を危険にさらさずに試す(公開 repo・シミュレータなし)

- **「実機の応答の再生」はシミュレータではない。** 既にモニタのテストがやっているとおり、実機で録った生バイト列/`GetChParam` の戻り値を固定して、解析と判定ロジックを単体テストする。公開して問題ないのは、機器の振る舞いを**生成**するものではなく、観測した事実を**記録**したものだから【判断。線引きはユーザー確認、§13】。
- **書き込み層の構造テスト**: モニタの `test_never_calls_a_set_function` を拡張し、制御アプリでは「`CAENHV_SetChParam` を呼ぶのは 1 関数だけ、渡せるパラメータ名は V0Set と Pw だけ」をソース走査で固定。
- **dry-run**: 本物のクレートに繋ぎ、読みは全部本物、書き込みだけ「書いたことにして」監査ログに出す。差分一覧・前提条件・SVMax 検査が本物の値で動くことを、何も変えずに確かめられる。`hv_control.py` の `--dry-run` の延長だが、**既定を dry-run にし、本番は明示フラグ**にする。
- **段階的コミッショニング**(実機作業はユーザー):
  1. 読み出しのみで数日運転(モニタと値が一致するか)。
  2. dry-run で操作手順を一通り。
  3. **検出器に繋がっていない予備 ch**(A1833 の空き ch、または PMT を外して終端)で V0Set の書き込み → 読み返し → ランプ監視 → トリップ(I0Set を低くして意図的に)→ 復帰、を実演。
  4. 1 ch の実 PMT を小さい Δ で。
  5. 全 ch。全 OFF と KILL はこの段階で 1 度は本当に押して結果一覧を見る(ビーム前)。
- 試験中は SVMax をさらに低く(運用値ぴったり)しておくと、ソフトのバグが出ても上に行けない。
- 機器のフェイク(パラメータ表を持つだけの偽クレート)をテスト用に作るなら、repo に入れてよいかはユーザー判断(§13)。入れないなら `tests/` 外の gitignore 配下か、再生テストだけで済ませる。

## 10. 既存のスロコン(EPICS / JCOP / WinCC OA)から借りるもの・借りないもの

| 慣行 | 何か | 借りる? |
|---|---|---|
| setpoint と readback を別の変数にする(EPICS の `:SET`/`:RBV` 流儀、MHV-4 RC バスの write/read アドレス分離) | 「要求」と「実際」を混ぜない | **借りる**(§3.3) |
| デバイス FSM(OFF/RAMP/ON/TRIPPED/UNKNOWN)【資料: MOPV009 Fig.6】 | ch の状態語彙 | **語彙だけ借りる**。SMI++ 的な階層 FSM は不要 |
| アラーム重要度(OK/WARNING/ERROR/FATAL)【同】 | 画面とログの色分け | **借りる**(4 段階で十分) |
| アーカイブ(全値の時系列保存)【同 §Requirements】 | 履歴 | **既にある**(InfluxDB/Grafana) |
| expert mode / shifter の分離【同 Chamber View】 | 役割分離 | 初版は「閲覧 / 書き込み(合言葉)」の 2 段、expert は後日 |
| 自動トリップ復帰、ビーム状態連動 | 自動化 | **借りない**(§4.5, §7) |
| OPC UA / PVSS データポイント生成器 | ミドルウェア | 借りない(規模が違う) |
| FSM の子→親への状態伝播(1 ch の ERROR で検出器全体が NOT_READY) | 集約 | 「24 ch 中 n ch 異常」の 1 行表示で足りる |

KISS の観点では、借りる価値があるのは**概念**(要求/実際の分離、UNKNOWN 状態、アラーム段階、監査)であって**基盤**ではない。

## 12. 初版の must-have と後回し

### 初版(N_Wall 向け、SY5527 の 24 ch だけ)

1. 読み出し: 全 ch の V0Set/VMon/IMon/Pw/Status/SVMax/I0Set/Trip/RUp/RDWn をタイムスタンプ付きで表示。UNKNOWN(読めない)を状態として持つ。
2. 書き込みは **V0Set と Pw** のみ。ソース走査テストで固定。
3. 書く前読み・前提条件(compare-and-set)・書いた後読み・ランプ監視(Status ビット)。
4. 拒否(クランプしない): SVMax 以上、Δ 上限超え、読み値が古い、SVMax 読めず、他人が変えた。
5. 差分プレビュー + コメント必須 + 操作者名必須 + 書き込み合言葉 + 編集モードの自動解除。
6. ALL OFF(Pw=0 全 ch)+ 結果一覧。KILL は別配置。
7. 監査ログ(append-only JSONL)+ Grafana 注記。外部変更の検出と記録。
8. 既定 dry-run、本番は明示フラグ。
9. 失敗は UI とログの両方に。rc は数値のまま。
10. Operator の Start 時 HV スナップショット(タイムアウトつき、取れなければそう記録)。

### 後回し

- 保護パラメータ(SVMax/I0Set/Trip/RUp/RDWn/PDwn/POn)の変更(expert ロールつきで)。
- 自動トリップ復帰(ch ごと、回数・間隔つき)。
- プリセット/グループ適用。
- Operator の Start インターロック(警告→阻止)。
- MHV-4 の制御(§8.2 の条件で)。
- ゲインマッチングの再構築(確認済みコマンド集合の反復として)。
- イベントモード、モニタとの接続 1 本化、アカウント管理。

## 13. ユーザーに決めてもらうこと

1. **SVMax / Trip / RUp / RDWn / POn / PDwn の運用値**(GECO で設定、ソフトは触らない)。特に SVMax を運用値 + 何 V にするか、Trip を何秒にするか。
2. **書き込みの認可方式**: §5.1 の (1)/(2)/(3) のどれか。初版は (2) を推奨。
3. **Δ 上限と ch ごとの運用上限**の数値(例 50 V/回、運用上限 = SVMax − 50 V)。
4. **全 OFF の手段**: ALL OFF(RDWn で降ろす)だけでよいか、KILL も UI に置くか。
5. **トリップ復帰**: 初版は手動のみでよいか。
6. **Start 時の扱い**: スナップショットのみ(推奨)か、HV 条件での Start 阻止まで要るか。阻止するならその条件(全 ch ON? Trip なし? V0Set と VMon の差 < x V?)。
7. **MHV-4**: 初版は範囲外でよいか(推奨)。後日やるなら「設定値が読めない」ままでよいか、Mesytec に V4.2 の状態読みコマンドを問い合わせるか。
8. **テスト用フェイク機器を repo に入れてよいか**(「シミュレータ公開禁止」の線引き)。入れないなら再生テスト + dry-run + 実機の予備 ch で賄う。
9. **クレート側のアカウント**: アプリ専用ユーザーを作るか、admin のままか。公開 repo にパスワードを置かない運用(docker/.env と同じ)にするか。
10. **監査ログの置き場と保存期間**(`/data` or `/archive`、ランデータと同じ扱いか)。
11. **A1833 のマニュアル**: CAEN ログインでユーザーが取得して `external/` に置くか(A1832 との差: 3 kV/3 mA、Trip 範囲、PDwn の既定値を確認したい)。
12. **GECO の併用ルール**: アプリが本番で動いているとき、GECO での変更を「禁止」にするか「可(アプリが外部変更として記録)」にするか。
