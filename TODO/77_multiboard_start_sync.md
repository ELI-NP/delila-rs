## 1. 発端 (2026-10-29)

N_Wall(V1725 PHA × 8 + VX2730)では、**VX2730 がマスター**になり、全ボードを S-IN で同期スタートする(ユーザー)。
スタート同期の実機テストの前に、Operator と Reader のスタートの手順をコードで確認した(ユーザー指示)。

## 2. コードの確認結果

**Operator**(`src/operator/client.rs`)

- `arm_all_sync`: 全コンポーネントに Arm を送り、**全台が Armed になるのを待つ**。
- `start_all_sequential`: pipeline_order ごとに(下流から)Start を並列に送り、そのグループが Running になるのを待つ。
  デジタイザは全部 order 1 なので、マスターとスレーブに同時に Start が届く。全台は Arm 済みなので問題ない。

**Reader**(`src/reader/mod.rs` の `send_arm_command` / `send_start_command`)

| ボード | スタート設定 | Arm で | Start で |
|---|---|---|---|
| DIG1(V1725/V1730) | `START_MODE_SW`(マスター) | 何もしない(Start まで遅らせる) | `armacquisition`(= 開始。Run を出力) |
| DIG1 | `START_MODE_S_IN`(スレーブ) | `armacquisition`(S-IN 待ち) | 何もしない(「already started on Arm」) |
| DIG2(VX2730) | `SWcmd`(マスター) | `armacquisition` | `swstartacquisition`(= 開始。Run を GPIO などに出力) |
| DIG2 | `SINlevel`(スレーブ) | `armacquisition`(S-IN 待ち) | `swstartacquisition`: S-IN が来れば成功、**来なければ約 1 秒待って CAEN −6** |

**結論:** 本番の構成(VX2730 マスター + V1725 スレーブ)は、今のコードで対応済み。逆向き(DIG1 マスター + DIG2 スレーブ)も動く(§3)。

## 3. 実ログでの裏付け(pf-qaq、2026-10-22)

ランごとの設定スナップショット(MongoDB、`/api/runs/<n>/config`)と Reader のログを突き合わせた。

|---|---|---|---|
| 17:08 の試行(4 回) | Run を出さない設定 | `SINlevel` | 約 1 秒待って −6「Command error」→ Running にならず失敗 |
| 121 | `OUT_PROPAGATION_SYNCIN` | `SWcmd`(両方 SW) | 成功 |
| **122** | **`OUT_PROPAGATION_RUN`** | **`SINlevel`** | **すぐに成功、同期して開始**(V1730 の開始の約 1 ms 前に返った) |

- 17:08 の失敗の原因は **S-IN に信号が来ていなかったこと**(ユーザー: V1730 の Run を TRG-OUT から出して VX2730 に入れれば同期スタートしていた)。
- **撤回の記録:** 最初は 17:08 のログだけを見て「DIG2 スレーブには必ず `swstartacquisition` が送られ、必ず −6 で失敗するバグ」と判断し、
  修正(S-IN スレーブでは何もしない)を計画した。ラン 122 の成功と照らし合わせて誤りと分かり、撤回した。
  その修正を入れていたら、S-IN が来ないときの大きな失敗(−6)が消え、「Running なのにイベント 0」という気づきにくい失敗に変わっていた。
  **今の −6 は「S-IN が来ていない」ことを知らせる正しい失敗なので、変えない。**

## 4. 本番の構成で残る弱点(今回は直さない)

DIG1 スレーブ(V1725)の Start は何もしないので、マスター(VX2730)の Run が届かなくても **Running を報告し、イベント 0 のまま気づきにくい**
(DIG2 スレーブの −6 とは逆)。対策案:

- (a) Operator 側: Running 中に、あるソースのイベント数が N 秒増えなければ警告する(FW に依存しない。Si は低レートなので N は長め)。
- (b) DIG1 のハードの取得状態を読む(パラメーター名と意味は CAEN の資料で要確認)。

当面は、Grafana のボード別レート(0 Hz が目立つ)と運用マニュアルの項目で補う。

## 5. テスト計画(pf-qaq、ランの合間に、ユーザーの了承と結線をもらってから)

**T1(本番と同じ向き): VX2730 マスター → V1730 スレーブ**

- 設定: VX2730 = `start_source: SWcmd`、`gpio_mode: Run`(または `trgoutmode: Run`) / V1730 = `startmode: START_MODE_S_IN`。
- 結線: VX2730 の GPIO(または TRG-OUT)→ V1730 の S-IN。共通のパルサーを両ボードの空き ch に入れる。
- 準備: pf-qaq の TOML で VX2730(source 1)を有効に戻す(今はコメントアウト)→ ランの合間に DAQ を再起動。
- 確認すること:
  1. Start が完了する(Operator のログに「Group order=1 all Running」)。
  2. 両ボードからイベントが来る(V1730 の 0 イベントは §4 の弱点なので、Grafana で特に見る)。
  3. `time_map.C`(TODO 72)でボード間のずれを測り、3 ラン繰り返してずれが一定か見る。
  4. Tune Up(SW スタートへの強制切り替え `force_software_trigger`)が両ボードで動く。

**T2(逆向き): V1730 マスター → VX2730 スレーブ** — ラン 122 で動作を確認済みなので省略してよい。

## 6. 結果

### 6.1 ラン 221 / 222(2026-10-29、pf-qaq、V1730 マスター → VX2730 S-IN スレーブ、設定は 10/22 のラン 122 と同じ)

- 構成: mod0 = V1730(`START_MODE_SW`、TRG-OUT = Run、内部クロック)、mod1 = VX2730(`SINlevel`、`clocksource = FPClkIn`)。
  同じパルサー(約 9.87 kHz)を **mod0 ch12** と **mod1 ch0** に入れた。各 約 21 秒。
- 解析: `pulser_dt.C`(`.delila` を TDelila で直接読む。ヒットの少ない ch の各ヒットに、もう一方の一番近いヒットを対応させる)。

| ラン | Δt = t(m0 ch12) − t(m1 ch0) の中央値 | RMS(±10 ns 内) | ラン中のずれ | 対応できた割合(m1 ch0 基準) |
|---|---|---|---|---|
| 221 | **−256.725 ns** | 0.281 ns | +0.0002 ns/s | 99.9 %(うち ±10 ns 外 5.3 %) |
| 222 | **−256.721 ns** | 0.282 ns | −0.0011 ns/s | 99.5 %(うち ±10 ns 外 5.1 %) |

- **同期スタートでの Δt は、ラン中も、ランを取り直しても一定**(差 0.004 ns)。ずれ(ドリフト)も無い → 時計は共有されている。
- ヒストグラムは 0.6 ns ほど離れた 2 本の山(細かい時刻の量子化と思われる。16 ns 刻みの調整には影響しない)。
- **mod0 ch12 にパルサーと無関係のヒットが約 36 kHz**(パルサーの周期の中で一様、電荷の中央値 1430 vs パルサー 7246)。
  このため、パルサーの約 5 % で mod0 側のヒットが欠ける(デッドタイムと思われる)。測定には影響しない。

### 6.2 ラン 223: mod0(V1730、マスター)の `start_delay` = 160 ns(2026-10-29)

設定は 6.1 と同じで、mod0 の `start_delay` だけ 0 → 160 ns(MongoDB の設定スナップショットで確認)。約 34 秒。

| ラン | `start_delay`(mod0) | Δt の中央値 | RMS | ラン中のずれ | 221/222 からの変化 |
|---|---|---|---|---|---|
| 221 / 222 | 0 | −256.72 ns | 0.28 ns | ≤ 0.001 ns/s | — |
| **223** | **160 ns** | **−416.766 ns** | 0.287 ns | −0.0004 ns/s | **−160.04 ns** |

- **向きが確定: ボードの `start_delay` を D 増やすと、そのボードの時刻は D 小さくなる**(CAEN の説明どおり、TODO 72 §6 の約束どおり = `sign=+1`)。
- 量も設定どおり(160 ns に対して 160.04 ns)。ラン中のずれは無く、幅も変わらない。
- **マスターに遅延を入れても、Run の出力は遅れない**(遅れるなら Δt は変わらないはず)。マスター自身の取得開始だけが遅れる。
  → 遅延はマスターにもスレーブにも入れられる。

### 6.3 ラン 224: mod0 の `start_delay` = 0、mod1(VX2730、S-IN スレーブ)の `rundelay` = 256 ns(2026-10-29)

目的: Δt をほぼ 0 にする(予想 −256.72 + 256 = −0.72 ns)。`rundelay` は `board.extra` で `/par/rundelay` に送った(スナップショットで確認)。

| ラン | mod0 `start_delay` | mod1 `rundelay` | Δt の中央値 | RMS | ラン中のずれ | 221/222 からの変化 |
|---|---|---|---|---|---|---|
| 224 | 0 | 256 ns | **+7.264 ns** | 0.282 ns | +0.0001 ns/s | **+263.98 ns** |

- **DIG2 の `rundelay` は S-IN(`SINlevel`)でのスタートにも効く。向きも DIG1 と同じ**(遅らせたボードの時刻が小さくなる → Δt は増える)。
- **ただし量が 256 ではなく 264 ns(1 クロック = 8 ns 多い)**。考えられるのは次の 2 つ:
  - (i) `rundelay` を 0 以外にすると 8 ns の固定の遅れが加わる(遅延 = 設定 + 8 ns)
  - (ii) スタートの取り込みが 1 クロックずれる(ランごとに変わりうる)
  - ラン 221/222 では取り直しても 0.004 ns しか変わらず、時計は共有なので (i) が有力。**次: `rundelay` = 248 で Δt ≈ −0.7 ns になるか**(なれば (i))。

### 6.4 ラン 225: mod1 の `rundelay` = 248 ns(2026-10-29)

| ラン | mod0 `start_delay` | mod1 `rundelay` | Δt の中央値 | RMS | ラン中のずれ | 221/222 からの変化 |
|---|---|---|---|---|---|---|
| **225** | 0 | 248 ns | **−0.734 ns** | 0.282 ns | +0.0004 ns/s | **+255.99 ns** |

- 予想(−0.72 ns)どおり → いったん (i)「設定 + 8 ns」で確定と判断した。**→ §6.6 で撤回(同じ 248 でも 8 ns 飛ぶランがあった)**。
  DIG1 の `start_delay` は設定どおり(160 → 160.04 ns)。
- **今の pf-qaq の 2 台は、パルサーで見て 0.7 ns 以内にそろった**(mod0 `start_delay` = 0、mod1 `rundelay` = 248)。
  残りの −0.73 ns は 8 ns 刻みより細かいので、ハードウェアではこれ以上詰められない(必要ならソフトの `timeSettings.json`)。

### 6.5 ラン 226〜229: `rundelay` の自動スキャン(2026-10-29、Operator REST から、各 20 秒)

「+8 ns は固定か、ジッタのような取り込みの揺れか」を見るため、mod0 `start_delay` = 0 のまま mod1 の `rundelay` を
248 → 8 → 0 → 248 と変えた(スクリプト `rundelay_scan.sh`、設定はスナップショットで確認)。

| ラン | mod1 `rundelay` | Δt の中央値 | `rundelay` = 0 からの変化 | 余分な遅れ |
|---|---|---|---|---|
| 221 / 222 / **228** | 0 | −256.72 / −256.72 / **−256.723** ns | — | — |
| **227** | 8 | **−240.713** ns | +16.01 ns | **+8** |
| 225 | 248 | −0.734 ns | +255.99 ns | +8 |
| **226** | 248 | **−8.688** ns | **+248.03 ns** | **0** |
| **229** | 248 | **−0.730** ns | +255.99 ns | +8 |
| 224 | 256 | +7.264 ns | +263.98 ns | +8 |

(RMS はどれも 0.28 ns、ラン中のずれは 0.001 ns/s 以下)

- **同じ `rundelay` = 248 でも、ランによって 8 ns 飛ぶ**(226 は +0、225 / 229 は +8)。§6.4 の「設定 + 8 ns で固定」は誤り。
  **実際の遅延 = 設定 + 0 または + 8 ns(ランごと)**。0 以外の 5 本では +8 が 4 本、+0 が 1 本。
- `rundelay` = 0 の 3 本は、すべて同じ値(0.003 ns 以内)だった。**→ §6.6 で、0 でも飛ぶことが分かった(下の 2 項目の推論は撤回)**。
  - S-IN の取り込みが際どい(NIM の Run 信号のジッタなど)なら、0 でも飛ぶはず。0 で 3 本とも飛ばないのは、
    「+8 が 8 割」の揺れが偶然そうなる確率では 1 % 未満 → **遅延の回路(ファームウェア)の側で起きている揺れ**と見るのが自然。
  - ただし本数が少ない。確定には、`rundelay` = 0 と 248 を各 5〜10 本取って、飛びの割合を見る。
- **実用上の結論:** VX2730 の `rundelay` を 0 以外にすると、ボードの時刻に **8 ns の不定**が残る(ランごと)。
  8 ns の不定が問題になる用途では、**VX2730 の `rundelay` は 0 のままにして、他のボードの遅延で合わせる**。
  - 今の pf-qaq は `rundelay` = 248(ラン 229 で Δt = −0.73 ns)。ランによっては −8.7 ns になる。

### 6.6 ラン 230〜247: 各設定 6 本ずつの自動スキャン(2026-10-29 夕方、各 20 秒)

ユーザーの経験: 「ランごとに 0, 8, 0, 8 と行ったり来たりしていた」。同じ設定を続けて取り、飛びの出方を見た
(スクリプト `delay_scan.sh` / 表は `delay_table.sh`、設定はスナップショットで確認、終了後は `start_delay` 0 / `rundelay` 248 に戻した)。
余分な遅れ = Δt − (−256.72 + `rundelay` − `start_delay`)。

| ラン | mod0 `start_delay` | mod1 `rundelay` | Δt (ns) | 余分な遅れ |
|---|---|---|---|---|
| 230 / 231 / 232 / 233 / 234 / 235 | 0 | 248 | −8.72 / −0.72 / −8.71 / −0.71 / −0.71 / −0.71 | 0 / **+8** / 0 / **+8** / **+8** / **+8** |
| 236 / 237 / **238** / 239 / 240 / 241 | 0 | 0 | −256.71 / −256.71 / **−248.71** / −256.71 / −256.71 / −256.71 | 0 / 0 / **+8** / 0 / 0 / 0 |
| 242 / 243 / 244 / 245 / 246 / 247 | 160 | 0 | −408.71 / −408.71 / −416.71 / −408.70 / −416.70 / −408.70 | **+8** / **+8** / 0 / **+8** / 0 / **+8** |

(RMS はどれも 0.278 ns。どのランも、ラン中は一定)

これまでの全ラン(221〜247、27 本)をまとめると:

| 設定 | 本数 | +8 ns になった本数 |
|---|---|---|
| 遅延なし(`start_delay` 0、`rundelay` 0) | 9 | **1**(238) |
| VX2730 `rundelay` 248 | 9 | 6 |
| VX2730 `rundelay` 8 / 256 | 各 1 | 各 1 |
| V1730 `start_delay` 160 | 7 | 4 |

- **遅延なしでも 8 ns 飛ぶ**(ラン 238)。§6.5 の「`rundelay` = 0 なら安定、遅延回路の揺れ」は撤回。
  **2 台の時間差は、ランごとに 0 か 8 ns のどちらかになる**(ラン中は一定)。行ったり来たりは規則的な交互ではなく、ランダムに見える。
- **飛ぶ割合は設定で変わるように見える**(遅延なし 1/9、遅延あり 12/18。偶然この差が出る確率は約 1 %)。
  VX2730 側(`rundelay`)でも V1730 側(`start_delay`)でも増える。V1730 の `start_delay` は Run の出力を遅らせない(§6.2)ので、
  VX2730 の S-IN の取り込みだけでは説明しにくい → **両方のボードのスタートの回路に、8 ns の不定がありうる**
  (V1730 の内部ロジックも 125 MHz = 8 ns、`start_delay` の刻みは 16 ns)。
- **2 台だけでは、どちらのボードが飛んだかは分からない**(Δt は相対値)。3 台以上にパルサーを入れれば、他とそろって動かないボードとして特定できる。
- **原因の切り分け(実験場で、手作業):** S-IN のケーブルを 1〜2 ns 分(20〜40 cm)長くする。
  取り込みの際どさ(ジッタ)が原因なら、飛ぶ割合が大きく変わる(0 か 100 % に寄る)。

### 6.7 まとめと N_Wall への影響(2026-10-29)

| 設定 | 向き | 量 |
|---|---|---|
| DIG1 `start_delay`(16 ns 刻み) | 遅らせたボードの時刻が小さくなる。マスターでも Run の出力は遅れない | 設定どおり + **ランごとに 0 / 8 ns の不定** |
| DIG2 `rundelay`(8 ns 刻み、`board.extra`) | 同上(S-IN スレーブで確認) | 設定どおり + **ランごとに 0 / 8 ns の不定** |
| 遅延なし | — | **ランごとに 0 / 8 ns の不定**(頻度は低い、1/9) |

- **ボード間の時間差には、ランごとに 8 ns の不定がある。ラン中は一定(0.01 ns 以内)。**
- **N_Wall への影響:** 中性子の TOF やボードをまたぐ同時計数で、8 ns のずれがランごとに入りうる。
  → **全ボードの最後の ch にパルサーを入れたまま取り、ランごとにボード間のずれを測って補正する**(TODO 72 §3.2 の「常時監視」)。
  ラン中は一定なので、ランの最初の数秒のパルサーで足りる。補正は `timeSettings.json`(ランごと)か、オフライン / root_sink で。
- 未確認: どちらのボードが飛ぶか(3 台以上で)、S-IN のケーブル長で頻度が変わるか、本番の向き(VX2730 マスター → DIG1 スレーブ、T1)。
