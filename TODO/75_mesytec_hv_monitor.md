## 2. MHV-4 のリモート仕様(データシート `MHV-4_V40_02`、mesytec.com、2026-10-22 取得)

接続は 2 通り(p.1/9, p.2/9): **USB(標準 USB-B)**、または mesytec control bus(RC バス、NIM Lemo。
MRC-1 / MRCC が必要)。**1 台なので USB で pf-qaq に直接つなぐ。** RC バスは使わない。

USB の通信設定(p.6/9 "Remote control via USB"):

- 9600 Bd、8N1(8 bit、パリティなし、ストップ 1)
- 「標準の ASCII 端末で操作できる」。**入力した文字はエコーされる**
- チャンネル番号 `c` = 0〜3(`4` か `a` = 全チャンネル)

**読み出しコマンド(p.6/9 "Read Commands")— 使うのはこれだけ:**

| コマンド | 内容 |
|---|---|
| `RU c` | 実際の電圧 |
| `RUP c` | 電圧の設定値(プリセット) |
| `RUL c` | 電圧の上限 |
| `RI c` | 実際の電流 |
| `RIL c` | 電流の上限 |
| `RP c` | 極性 |
| `RT c` | 温度センサー入力 c の温度 |
| `RTC c` | 温度補償の設定 |
| `RRA` | 電圧のランプ速度 |

**設定を変えるコマンド(p.6/9 "Set Commands")— 送ってはいけない:**
`ON`、`OFF`、`SU`、`SUL`、`SIL`、`SP`、`AS`、`STC`、`STO`、`STS`、`SRA`。
特に `SP`(極性の変更)は、HV が出ていると自動で切って 0 V にする(p.6/9)。

### 2.1 実機での確認(2026-10-22、pf-qaq、ユーザー了承済み、読み出しコマンドのみ送信)

固定パスを 9600 8N1・フロー制御なしで開き、コマンドの後ろに CR(`\r`)を付けて送った。ch 0〜3 + `RRA` の 25 個。
このとき 4 ch とも 0 V だった。

| コマンド | 応答(生のバイト列、例) | 読み取り |
|---|---|---|
| `RU 0` | `RU 0\n\rU0: +0.0\n\rMHV-4>` | 電圧 [V]、小数 1 桁、符号付き |
| `RUP 0` | `RUP 0\n\rERROR!\n\rMHV-4>` | **使えない**(V4.2 では未対応。データシート V4.0 にはある) |
| `RUL 0` | `RUL 0\n\rUlim 0: +27.50\n\rMHV-4>` | 電圧の上限 [V](ch 3 は `+110.2` で、桁数が ch によって違う) |
| `RI 0` | `RI 0\n\rI 0: -0.004 uA\n\rMHV-4>` | 電流 [µA]、小数 3 桁(1 nA)、負の値もありうる |
| `RIL 0` | `RIL 0\n\rIlim 0: 20.000 uA\n\rMHV-4>` | 電流の上限 [µA] |
| `RP 0` | `RP 0\n\rPolarity 0: positive\n\rMHV-4>` | 極性 |
| `RRA` | `RRA\n\rMHV ramp speed: 5 V/s\n\rMHV-4>` | ランプ速度 |

- **応答の形**: 送ったコマンドのエコー → `\n\r`(LF CR の順)→ 値の行 → `\n\r` → プロンプト `MHV-4>`。
  **プロンプト `MHV-4>` を応答の終わりの印にする。** エラーは `ERROR!`。
- 値は「ラベル: 数値 [単位]」の形。解析は「`:` の後ろの数値 + 任意の単位」とし、桁数は固定しない。
- 0.8 秒待てば全部返ってきた(応答時間そのものは未測定)。
- **電圧の設定値(プリセット)が読めない**(`RUP` が `ERROR!`)。**ON/OFF の状態を読むコマンドもない**。
  → 当面は `vmon`(`RU`)・`vlimit`・`imon`・`ilimit`・`polarity`・`ramp` を記録する。
  データシートにないコマンドを手探りで送ることはしない。

### 2.2 ON/OFF の表示(ユーザー要望、2026-10-22)

**ON/OFF は Grafana に出したい。** ただし過去に LabVIEW で MHV-4 を扱ったとき、**LabVIEW 側が ON/OFF を
自分で覚えていた**ため、フロントパネルで ON/OFF すると表示と実機が食い違い、おかしなことになった(ユーザー)。

方針:

1. **ON/OFF をソフトウェア側で覚えない。** 表示するのは、毎回実機から読んだ値と、その値から計算したものだけ。
   モニタを再起動しても、フロントパネルで操作しても、表示が実機とずれない形にする。
2. **Mesytec への問い合わせはしない**(ユーザー: 返答は期待できない)。**データシート V4.0_02 のコマンドで進める。**
   V4.0_02 には ON/OFF の状態を読むコマンドがないので、次の 3. を正式な表示にする。
3. **「HV が出ているか」を測定値から出す。** `|vmon|` がしきい値(1 V)を超えたら「HV あり」。
   ON/OFF そのものではない(ON で設定 0 V のときや、ランプ中は区別できない)ので、ダッシュボードでは
   「ON/OFF」ではなく「HV 出力あり / なし(電圧から判定)」と書く。

**データシートに書かれていないこと(上の確認で 1・2 は解決、3 は「読めない」と確定):**

1. 応答の書式と行末の文字(エコーの後ろにどう値が返るか)
2. `RU` / `RI` の単位(設定コマンドの単位は 0.1 V と nA。表示の分解能は電流 1 nA、電圧 12.5 mV、p.2/9)
3. **チャンネルの ON/OFF 状態を読むコマンドがない。** 電流上限を超えたとき(ブザーと LED の点滅、p.5/9)の状態も読めない。
   ON/OFF は `RU` と `RUP` の比較で推定するしかない可能性がある
4. 手元の個体のファームウェア(Product 名は `MHV4_V42`、データシートは V4.0 用)でコマンドに違いがないか
5. ~~USB がどのデバイスとして見えるか~~ → 確認済み(上記、FTDI `/dev/ttyUSB0`)

## 3. 設計案

1. **`tools/hv_monitor/mhv4_monitor.py`**: 既存の `hv_monitor.py`(N1408、同じく 9600 Bd のシリアル)と同じ形。
   2〜5 秒ごとに 4 ch × 読み出しコマンドを送り、InfluxDB の `/api/v3/write_lp?db=delila` に書く。
   9600 Bd で 1 コマンド数十ミリ秒なので、1 周期 30 コマンド程度でも十分間に合う。
2. **安全装置**: 送信関数は `R` で始まる上の表のコマンドしか通さない(許可リスト)。許可リストのテストを書く。
3. **InfluxDB のテーブル**: 新しく `mhv4` を作る(推奨)。タグ `channel`、フィールド `vmon`・`vlimit`・
   `imon`・`ilimit`・`polarity`(`vset` は §2.1 のとおり V4.2 では読めない)。ランプ速度は全体で 1 つ。温度はセンサーがないので今は読まない(つないだら `RT` を足す)。
   既存の `hv_monitor`(N1408)に混ぜると、`status` の意味が違うので、Fission2026 のダッシュボードと食い違う。
4. **ダッシュボード**: 「Si HV (MHV-4)」を新しく作る(TODO 74 の P4「Si + 中性子」にもパネルを置く)。
5. **常駐**: DAQ(Operator)とは**独立したプロセス**として、`hv_launcher.py` に登録し pf-qaq で systemd から起動。
   DAQ の起動・停止とは連動させない。ポートは by-id の固定パスで開く。`dialout` の権限は sudo が要る。
6. **操作(将来)**: 要望が出たら、DAQ とは別の Web アプリにする。その場合もシリアルポートは 1 プロセスしか開けないので、
   読み出しモニタと操作アプリが同じポートを取り合わない形(1 プロセスにまとめる等)をそのとき設計する。
7. **テスト**: 応答の解析は、実機で取った応答を使った偽のシリアルで単体テスト。そのあと実機で確認。
