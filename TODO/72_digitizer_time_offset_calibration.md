## 1. 発端 (2026-10-07)

デジタイザ自身にも時刻オフセットを設定できる。ユーザーが考えたいのは次の 2 通り。

- **(a) パルサー方式:** 各デジタイザに共通のパルサーを入れ、時間差からオフセットを決める。
- **(b) 実験データ方式:** 実験データの時間差を見てオフセットを決める。

いずれも**自動で設定まで行うシステム**にしたい。マルチデジタイザ環境で、ボード間の相関を見るための前提になる(TODO 71 Phase D)。

## 2. 今あるもの

### 2.1 ハードウェア側で設定できるもの(DevTree の実機ダンプ `docs/devtree_examples/` から)

| 設定 | FW | 対象 | 範囲・刻み | 意味 |
|---|---|---|---|---|
| `/par/start_delay` | DIG1(PSD1/PHA1) | ボード | 0〜4080 ns、16 ns | 同期スタートの遅延 |
| `/par/rundelay` | DIG2 | ボード | 0〜524,280 ns、8 ns | RUN 信号の立ち上がりに対するスタートの遅延 |
| `/par/volatileclockoutdelay` | DIG2 | ボード | ±18.9 ns、74 ps | クロック出力の位相(デイジーチェーンのクロック合わせ)。`permanent…` は flash に保存 |
| `/group/N/par/inputdelay` | DIG2 PHA2 | 4 ch 単位 | 0〜4095 | 入力信号の遅延 |

- DELILA の設定には `start_delay`(ボード)と `group_input_delay`(PHA2)が既にある(`src/config/digitizer.rs:854,879`)。
- **ハードウェアで合わせられるのは、主にボード単位の粗い調整(8〜16 ns 刻み)**。
- DIG2 のクロック位相だけは 74 ps 刻みで合わせられる。
- チャンネル単位の細かい調整は、ハードウェアではほぼできない。

### 2.2 ソフトウェア側

- `timeSettings.json`(木構造、(module, channel) 単位、任意の精度)。Rust EB と root_sink(TODO 70)が入口で 1 回適用する。`.delila` は生の時刻のまま。
- 測るツール:
  - Rust の `event_builder time-calib`: `.delila` から、基準 ch に対する時間差のピークを求める。出力は旧形式。木構造の自動生成は SPEC §4.3.5 で計画のみ。
  - ELIFANT-Event の TimeAlignment: 同じ考え方。
  - `tools/root_sink/delayline_offsets.C`: ThGEM のディレイライン専用(像の中心合わせ)。

### 2.3 大前提: ボードが同じ時間軸で動いていること

独立にスタートしたボード(`START_MODE_SW`)同士は、時計がずれていく。この状態ではオフセットは定数にならず、較正できない。

**共通クロック + 同期スタート**が必要。
- 配線: CLK-OUT → CLK-IN のデイジーチェーン、TRG-OUT → S-IN。
- 設定: スレーブは `START_MODE_S_IN` + `OUT_PROPAGATION_SYNCIN`、マスターは `START_MODE_SW` + `OUT_PROPAGATION_RUN`。

同期すると、ボードごとに一定のスタート位相のずれが残る(ELIADE の想定、TODO 59)。**これが較正の対象**。今の pf-qaq(ThGEM)は、独立した時間軸の構成。

## 3. 考え方(たたき台)

### 3.1 二段構え
1. **ハードウェアで粗く合わせる(ボード単位):** スタートの遅延(8/16 ns 刻み)と、DIG2 のクロック位相。必要になるのは、ボード間のずれが大きいときや、ハードウェアのトリガー論理をボードにまたがって組むとき。
2. **ソフトで細かく合わせる((M,C) 単位):** 粗い調整の残差とケーブル差を `timeSettings.json` で補正する。任意の精度で、元の `.delila` には手を加えない。

### 3.2 パルサーとデータの比較

| | パルサー | 実験データ |
|---|---|---|
| ピーク | 鋭い(電子回路だけ) | 検出器の応答次第(walk、Ge の遅い立ち上がり) |
| いつ測れるか | いつでも。ビームが無くてもよい | 即時の同時計数が十分に溜まってから |
| 分かるもの | **ボード単位**(パルサーを入れた ch の差) | **ch 単位**(ケーブル差まで) |
| 必要なもの | ファンアウトと、各ボードの空き ch | 追加ハードウェアは不要 |
| 副産物 | ラン中も入れておけば、**ずれの常時監視**になる(位相跳び、同期外れの検出) | — |

→ **組み合わせが自然:** パルサーでボード単位を合わせて常時監視し、データで ch 単位を合わせる。

### 3.3 自動化の流れ(案)
1. Operator に「時刻較正ラン」を設ける(パルサーを入れる、または指定時間データを取る)。
2. 解析(root_sink のように同じ流れの中で、またはオフラインで)が、基準に対する時間差のピークを (M,C) ごとに求める。
3. **提案を出す:** ハードウェアの値(刻みに丸めたもの)と、ソフトの残差(`timeSettings.json`)。
4. 操作者が確認してから適用する。デジタイザの JSON(`start_delay` / `rundelay` など)と `timeSettings.json` に書く。
5. 確認ランを取り、残差が許容範囲内であることを見る。MongoDB / eLog に記録する。
- **安全面:** ラン中に勝手に適用しない。ハードウェアの値は必ず人の確認を挟む。どの値で取ったかは、ランごとに記録する(TODO 70 の provenance と同じ考え方)。

## 5. ユーザーとの合意 (2026-10-07)

- **共通クロックの配布と同期スタートは必ず行う**(実験の運用上の前提)。§2.3 の前提は満たされているものとする。
- **精度は 16 ns 刻みで十分すぎる:** 同じボードの中でも、ch 間にその程度のずれはある。
  - → **ハードウェアの粗い調整(DIG1 `start_delay` 16 ns、DIG2 `rundelay` 8 ns)だけで目的を果たせる。**
  - ソフトでの細かい調整(`timeSettings.json`)は、この TODO の必須要素ではない。ThGEM のディレイラインの中心合わせのような ch 単位の用途は、TODO 70 で別に扱う。
- **空き ch の問題はある。** それでも、**各ボードの最後の ch にパルサーを入れて、実際にずれるかを確認することは絶対に必要。**

### 較正の手順(合意)

1. **較正ラン:** 各ボードの**最後の ch = 共通パルサー**(ファンアウト)、それ以外の ch = 検出器。ビームなどで、検出器同士の時間差を測る。
2. **パルサーの ch 同士の時間差も測る**(ボード間の電子回路の素のずれ)。
3. **検出器で測ったずれをもとに、ボードごとにハードウェアの値を調整する**(刻みに丸める)。
   - 調整は物理の信号(検出器、ケーブル)に合わせる。パルサーは合わせる対象ではなく、確認に使う。
4. **パルサーが期待どおりに動いたかを確認する:** 次のランで、パルサーの時間差が、**入れた調整量どおりに**変わったかを見る。
   - → 設定が実際に反映されたこと、ボードが想定外に跳んでいないことの確認になる。

### この手順から決まること、残る問い

- 解析は、パルサーの ch と検出器の ch を分けて扱う。設定で「各ボードの最後の ch = パルサー」と指定し、ボードごとに次の 2 つを出す。
  - 検出器から見たずれ
  - パルサーから見たずれ
- **ボードの代表値の取り方(未決):** ボード内の検出器 ch のずれの中央値にするか、ボードごとに基準 ch を決めるか。ボード内の ch 間の差(16 ns 未満)は、そのまま受け入れる。
- **確認の判定:** パルサーの時間差の変化量 − 入れた調整量 が、刻み(8/16 ns)の半分以内なら OK、など。
- **パルサーを通常のランでも入れたままにするか**(常時監視)、較正時だけにするか(空き ch の問題とのかね合い)。
- 検出器の時間差に使う同時計数(即時のγ-γ、Si-HPGe など)は、実験ごとに決める。統計がどれだけ要るか。
- 自動化の範囲: どこまで自動にするか(解析と提案まで自動、適用は人の確認の後、が安全側)。


## 6. 測定ツール `time_map.C` (2026-10-07、TODO 71 Phase D2)

`tools/root_sink/time_map.{hpp,C}` + `test_time_map.cpp`(244 チェック)。入力は hits ツリー(delila2root の出力、または root_sink の `--hits-tree`)。

| 関数 | 中身 |
|---|---|
| `time_map_offsets` | 基準 ch に対する各 ch の Δt ピーク(背景を引いた中央値が既定)→ `timeSettings.json`(木構造)。ボードごとの中央値と、ボードの合計ヒストグラムのピークも出す。ピークの無い ch は一覧に出す |
| `time_map_boards` | §5 の手順。ボードの**検出器から見たずれ**からハードウェアの遅延の変更量を提案(16 ns / 8 ns に丸める)し、変更後に期待されるパルサーの時間差も出す。各ボードの最後の ch をパルサーとみなす(指定も可) |
| `time_map_verify` | 次のランで、パルサーの時間差が入れた変更量どおりに動いたかを、ボードごとに PASS / FAIL |
| `time_map_ac` | どの shield(BGO)がどの検出器グループの担当かを、即時の同時計数の割合から判定し、ペアごとの Δt を出す。event_def v1.1 の `tags` + `anti_compton` を書き出す。あいまい・無反応の shield は名指しで出す |

**向きの約束(未確認):** ボードの遅延を D 増やすと、そのボードの時刻は D 小さくなる(CAEN の説明から)。実機の最初の確認ランで決まる(逆なら `sign=-1`)。

### ELIFANT p+¹⁴⁰Ce run 112 での結果(11 ボード、4,130 万ヒット、1 回およそ 10 s)

- **AC の担当:** 位置タグごとの 24 グループ × BGO 25 ch で、**ELIFANT の HasAC と 24/24 一致**(+B2 = m9c10 ↔ m8c6 のような非自明な組も)。γ カスケードのため全組み合わせが有意になるが、相手の割合が最大でも本命の約 11 % なので、優位性の規則(0.5)で正しく分けられる。
- **ボード間のずれ**(基準 LaBr3 m9c0、中央値):

| ボード | 中身 | ずれ (ns) |
|---|---|---|
| m0 | ΔE セクター | −107 |
| m1 / m2 / m3 | ΔE リング | −47 / −274 / −224(合計ヒストグラムから) |
| m4 | E セクター | −418 |
| m5 / m6 / m7 | E リング | −267 / −160 / −131 |
| m8 | BGO | +80 |
| m9 | LaBr3/CeBr3(基準) | 0 |
| m10 | HPGe | +107 |

  - **16 ns 単位では揃っていない**(ELIFANT の時刻合わせの表はすべて 0 だった)。同じ種類の検出器(E リング m5/m6/m7)でも最大 140 ns ずれる → ボード間のずれ、または FW のトリガー設定の違い。ELIFANT の 2000 ns の窓では見えていなかった。
  - ずれには検出器そのものの応答も入っている(BGO の +80 はほぼシンチレータ、Si は −100〜−400)。§5 の方針(物理の信号に合わせる)どおりだが、「ボードのずれ = 電子回路のずれ」ではない。パルサーを入れれば `pul-det` の列で両者を分けられる。
  - この run では Si のリングを基準にできない(Si 同士の Δt が櫛状のスパイク)→ LaBr3 を基準にする。
- **AC の窓の提案:** HPGe を含めると [−255, +165] ns(HPGe の幅広いピークで決まる)、LaBr3 だけなら [0, +158] ns。
- **パルサー無しのため:** `time_map_boards` / `time_map_verify` は、合成データの単体テスト(既知のずれ、逆向き、調整し忘れのボード)と、各ボードの最後の ch を仮のパルサーにした試験(変更を反映したファイルで 6 PASS、反映しないと 6 FAIL)で確認。

### 残っていること

- **実機での確認:** パルサーを各ボードの最後の ch に入れた複数ボードの構成(例: SN05 の V1725 × 3、ELIADE)で、計画 → `start_delay` を変える → 確認ラン → `time_map_verify`。ここで遅延の向きが確定する。
- **AC の窓がペアごとに 1 つ:** event_def v1.1 の AC の窓は全ペア共通。HPGe と LaBr3 を混ぜると幅広くなる。ELIADE は Ge だけなので当面は問題にならない。必要になればペアごとの窓を足す。
- **Operator からの自動化**(§3.3): 較正ランの指定、解析、提案、人の確認の後の適用、MongoDB / eLog への記録。
