## 2. 今の状態(pf-qaq、実測)

## 3. 圧縮方式の比較(2026-11-03、pf-qaq)

| 方式 | 圧縮率 | 圧縮の速さ(入力) |
|---|---|---|

| `zstd -1`、1 スレッド | 2.43 倍 | 267 MB/s |

## 4. 方針(ユーザー、2026-11-03)

### 4.1 いつ・どこで: ファイルを移すときに、mv の代わりになるツールで

【判断】現実的。`archive_sync.sh` と同じく bash + zstd の CLI で 100〜150 行程度(仮名 `scripts/delila_mv.sh`)。

- 使い方は mv と同じ: `delila_mv.sh SRC... DEST_DIR`。
- `.delila` ごとに: `DEST/<名前>.delila.zst.part` に圧縮 → `sync` → **移動先のディスクから読み直して確認** →
  `.part` を本来の名前に変える → **最後に元を消す**。確認が 1 つでも失敗したら元は消さず、`.part` も残さない。
- 確認は 2 段: (a) zstd のフレームのチェックサム(`zstd -t`)、(b) **`.delila` 自身のフッタにあるデータのチェックサム**
  (xxHash64、`recover validate`)。(b) は §4.2 で `.zst` を直接読めるようになれば、元のファイルを読み直さずに確かめられる。
  フッタの無いファイル(異常終了したラン)は、展開したものを元と `cmp` で比べる。
- 落とし穴: 書いた直後に読み直すと、ディスクではなくメモリ上のキャッシュから読んでしまう。Linux では、確認の前に
  そのファイルのキャッシュを捨てる(`dd if=F iflag=nocache count=0` など)。
- `.delila` 以外(`.root`、`.json`): 圧縮せずにコピー → `cmp` → 元を消す(同じファイルシステム内なら普通の mv)。
- 移動先に同じ名前があれば上書きしない。途中で止まっても、残るのは `.part` だけ(次に実行したときに消す)。`--dry-run`、ログ、縮んだ量の集計。

### 4.2 `.zst` を直接読む

【判断】現実的。今の読み込み(Rust の `DataFileReader`、C++ の `TDelila.hpp`)はどちらも、最初にファイルの末尾へ飛んで
64 バイトのフッタを読み、それから先頭から順に読む。zstd のストリームは前後に飛べない。

- **一番簡単な方法: ファイル全体をメモリに展開してから、今の読み込みにそのまま渡す。** `.delila` は Recorder が
  `max_file_size_mb`(既定 1 GiB)で分けているので、1 ファイルは 1 GiB 程度。展開は約 1 秒(§3.1)。
  Rust は `Cursor<Vec<u8>>` が Read + Seek なので `DataFileReader` は変えずに済む。C++ はメモリ上のバッファから読む `istream` に差し替える。
- 展開後の大きさは zstd のフレームの見出しに入っている(zstd の CLI はファイルを圧縮するとき書く)。
  大きすぎる場合(`max_file_size_mb` を大きく設定したラン)は、展開してから読むよう案内するエラーにする(黙って遅くしない)。
- Rust: `zstd` クレート(libzstd を同梱してビルド、システムのライブラリは不要)。`DataFileReader` を開く場所で拡張子を見る。
  → `recover`、`event_dump`、`event_builder`、各リプレイ、`pha_trap_tune`、`pha_fw_scan` がまとめて対応する。
- C++ `TDelila.hpp`: 「依存なし」を守る。コンパイル時に指定すれば libzstd を使い、指定しなければ `zstd -dc` をパイプで
  呼んで読む(実行するホストに zstd の CLI が要る。Linux の DAQ ホストにはある、Mac は brew)。
- テスト: 小さな `.delila` を圧縮して、`.delila` と `.delila.zst` から読んだイベントが完全に一致すること(Rust と C++ の両方)。

## 5. 決定(ユーザー、2026-11-03)

1. **移動先 = sshfs か NFS でマウントしたネットワークストレージ**(ツールから見ればローカルのパス。rsync は使わない)。回線は 1 Gb(約 120 MB/s)。
2. **zstd -3 を既定、容量優先なら -9。** 条件: 圧縮が回線(1 TB を生でコピーして 8000〜10000 秒)より速いこと。
   - 【実測からの見積もり】pf-qaq の `zstd -3 -T8` は約 750 MB/s(波形なし、入力側)= 1 TB を約 22 分 → 回線より 6 倍以上速い。
     圧縮すると回線を通るのは 1/2.6(波形なし)〜1/6.6(波形入り): 1 TB が 383 GB(約 53 分)〜150〜190 GB(約 21〜26 分)。
     **回線が律速で、生のコピーより 2.6〜6 倍速く終わる。** 移動先から読み直す確認で回線をもう 1 回使う(合計で波形なし約 1.8 時間、波形入り約 0.8 時間)。
   - `-9` は pf-qaq で約 200 MB/s(波形なし、8 スレッド)→ 1 TB 約 85 分(圧縮が律速)。それでも生のコピーより速い。
3. **xz は使わない。** 保存先のネットワークストレージは約 128 PB あり、容量は問題にしない → zstd だけ。
4. **実装する**(順番: ① Rust の読み込み + `recover validate`、② `TDelila.hpp`、③ `delila_mv.sh`)。

### 使い方

```bash
# 終わったランを、マウントしたネットワークストレージへ(.delila は .delila.zst に、ほかはそのまま)
scripts/delila_mv.sh /data/N_Wall/run0004_* /mnt/storage/N_Wall/
scripts/delila_mv.sh -n /data/N_Wall/run0004_* /mnt/storage/N_Wall/   # 何をするかだけ表示
scripts/delila_mv.sh -l 9 ...                                          # 容量を優先
```

- 元のファイルを消すのは、移動先から読み直して元とバイト単位で一致し、本来の名前に変えた後だけ。移動先に同じ名前があれば上書きしない。
- 10 分以内に書かれたファイルと root_sink の `run_inprogress_*` は動かさない(`--min-age`)。
- 移動先が元と同じファイルシステムなら止まる(マウントし忘れで、空のマウント先 = ローカルのディスクに書いてしまうのを防ぐ。`--same-fs` で許可)。
- 1 つでも動かせなかったら終了コード 1、そのファイルは元の場所に残る。
